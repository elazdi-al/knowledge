## From Data to a DBMS

Modern software is useful only when data can be stored, shared, and queried correctly over time. The starting point is the difference between raw facts and meaning.

**Data.** Raw facts used as input for reasoning and computation. Data may be useful, irrelevant, or redundant, and must be processed before it carries meaning.

**Information.** Data that has been organized and processed so that it is relevant to a problem and actionable for a decision. The flow is $\text{data} \xrightarrow{\text{organize}+\text{process}} \text{information}$, which in turn supports knowledge and wisdom.

Once facts carry meaning, they need structure. A **database** is a large, integrated, structured collection of data that models a real-world enterprise. The two things it organizes are **entities** (object types we store data about, such as a student or a course) and **relationships** (meaningful associations between entities, such as a student enrolling in a course).

A database on its own is passive, so we need software to manage it.

**Database Management System (DBMS).** A software system that stores, manages, and provides access to databases. It decomposes as $\text{DBMS} = \text{database} + \text{programs to access and manage it}$, and its core role is efficient, reliable, convenient, and safe multi-user access to massive persistent data.

That sentence packs several guarantees that a plain file system does not provide.

- **Persistence.** Data outlives any single process or program execution.
- **Concurrency control.** Simultaneous operations are coordinated so outcomes stay correct.
- **Recovery.** Failures of hardware, software, or power do not corrupt the stored data.
- **Declarative access.** Queries are stated at a high level, with physical data independence from how bytes are laid out.

The reason a file system is not enough is the missing contract. *If two collaborators save the same file at nearly the same time, whose changes survive is unclear; if power fails mid-write, which changes survive is unclear.* When durability, isolation, and recovery are not explicit, every application has to re-implement them, so the DBMS exists to supply these guarantees systematically. The web has the same gap in a different form: it is strong at retrieval, but its data is unstructured, completeness is not guaranteed, and consistency and freshness are weak, so serious sites place a DBMS behind the web layer rather than treat the web as one.

**Ad-hoc query.** A query formed for a specific immediate need rather than predefined as part of a fixed workflow. Supporting ad-hoc querying, alongside concurrency control and recovery, is precisely what raises a DBMS above storage.

## Describing Data Across Levels

The central architectural question is how to keep one coherent meaning of the data while serving many users and storing bytes efficiently. The answer is to describe data with a model and to separate that description into levels.

**Data model.** A collection of concepts for describing data. A model is a high-level abstraction: it hides storage details so we can reason about structure and meaning first. The dominant family is the **relational model**, where data is a set of records organized into relations.

- **Relation.** A named table with rows (tuples) and columns (attributes).
- **Schema.** The structural definition of a relation: its attribute names, types, and organization.

Schema is the type and data is a value following that type, the same way *string* is a type and *"hello"* is a value. A relational schema names attributes with their types explicitly.

*Example. University schema. The relations are `Students(sid:string, name:string, login:string, age:integer, gpa:real)`, `Enrolled(sid:string, cid:string, grade:string)`, and `Courses(cid:string, cname:string, credits:integer)`. Explicit typing in the schema is the point.*

The same database is described at three levels of abstraction, and the schema at each level can change without disturbing the level above it.

- **External schema.** User- or application-specific views, often used for access control. *Examples: `Students_Info(sid, name)` view; `Course_Enrollment(cid, #enrolled)` summary.*
- **Logical (conceptual) schema.** The single global structure that users and application programs see. *The university relations.*
- **Physical (internal) schema.** How data is stored: files, indexes, and layout. *Relations stored as unordered files with indexes on `Students.sid` and `Courses.cid`.*

The mapping runs $\text{external schemas} \rightarrow \text{logical schema} \rightarrow \text{physical schema}$: many external views map onto one logical schema, which is then realized by physical structures.

**Data independence.** The ability to change the schema at one level without changing the schema at the next higher level. **Logical data independence** changes the conceptual schema without touching user views; **physical data independence** changes the internal schema without touching the conceptual schema or views. This matters because storage layouts and indexes improve constantly, and applications should keep working while they do.

The relational level connects relations through their values. A **key** is an attribute (or set of attributes) whose value uniquely identifies a tuple inside a relation, and a **foreign key** is an attribute in one relation whose values reference the keys of another, linking the two.

*Example. Enrolled references Students. In `Enrolled`, the column `SID` is a foreign key referencing `Students.SID`, so a row like `(53666, Carnatic101, 5)` only makes sense when `53666` also appears as a student. This is how rows in separate relations are tied together.*

Database design proceeds through requirements analysis, conceptual design, logical design, schema refinement, physical design, and security design. Conceptual design has its own modeling language.

**Conceptual design.** A high-level description of the enterprise data, independent of storage and implementation. It answers three questions: which entities and relationships exist, what information about them to store, and which integrity constraints must always hold. Its standard language is the Entity-Relationship model, and the resulting **ER diagram** maps cleanly into a relational schema.

## Entities, Attributes, and Relationships

The ER model captures entities, their attributes, relationships, and constraints before any logical or physical decision is made. The first three building blocks describe what exists.

**Entity.** A real-world object, distinguishable from every other object.

**Attribute.** A property used to describe an entity, drawing its values from a **domain**, the set of values that attribute is allowed to take.

**Entity set.** A collection of similar entities that share the same attributes. Its **key** is an attribute, or minimal set of attributes, that uniquely identifies the entities in the set. In an ER diagram an entity set is a rectangle, an attribute is an ellipse joined to it, and the key attribute is underlined.

An **instance** of an entity set is the collection of entities currently stored in it. *For `Employees`, the instance might be `(123-22-3666, John, P1)` and `(231-31-5368, Tom, P2)`: two concrete employees, each a tuple over the declared attributes.*

Entities become useful when they are associated.

**Relationship.** An association among two or more entities. A **relationship set** is a collection of similar relationships, drawn as a diamond joining the participating entity sets, and a relationship may carry its own attributes.

*Example. Works_In. `Works_In` links `Employees` and `Department` and records when the assignment began through the descriptive attribute `since`, an attribute of the relationship rather than of either entity.*

## Constraints on Participation

A relationship set by itself allows any entity to take part in any number of relationship instances. Constraints sharpen this into precise cardinality. The two independent dimensions are how many instances one entity may join (key constraints) and whether every entity must join at least one (participation constraints).

**Key constraint.** A restriction stating that each entity in a set participates in at most one relationship instance of a given relationship set. In the diagram it is drawn as an arrow from the entity set to the relationship. Placing arrows on neither, one, or both sides yields many-to-many, one-to-many, and one-to-one relationships.

## Weak Entities

Some entities have no key of their own and exist only relative to another entity. They are identified partly by a neighbor.

**Weak entity.** An entity that can be identified uniquely only by combining its own partial key with the primary key of an owner entity. Its **identifying relationship** links it to that owner, and the weak entity must have total participation in this relationship.

A weak entity set obeys three structural rules.

- **Ownership.** Owner and weak entity set participate in a one-to-many relationship: one owner, many weak entities.
- **Total participation.** The weak entity set participates totally in the identifying relationship, since no weak entity exists without an owner.
- **Partial key.** The weak entity has only a partial key, drawn with a dashed underline, which identifies it only within the scope of one owner.

The weak entity and its identifying relationship are drawn with thick borders, and the arrow from the weak entity marks the key constraint.

## ISA Hierarchies

Sometimes an entity set has subgroups that carry extra attributes or join their own relationships. ISA captures specialization while keeping shared attributes in one place.

**ISA hierarchy.** A relationship between a superclass entity set and one or more subclass entity sets, where every subclass entity is also a member of the superclass and inherits all of its attributes. Declaring A **ISA** B means each A entity is a B entity and has every attribute of B, plus the specialized attributes A adds for itself.

Two orthogonal constraints govern how the subclasses relate to the superclass. The **overlap constraint** asks whether an entity may belong to more than one subclass at once, defaulting to no (disjoint). The **covering constraint** asks whether every superclass entity must belong to some subclass, defaulting to no (partial coverage). We use ISA either to add descriptive attributes specific to a subclass, or to identify exactly the entities that take part in some relationship.

These two defaults are not fixed; a single superclass can have several specialization branches with different overlap behavior.

*Example. Student hierarchy. A `Student` is classified by degree (Bachelor or Post-Graduate) and by status (Full-time or Part-time) at the same time, so these are two overlapping branches off the same superclass. Within each branch the subclasses are non-overlapping: a student is a Bachelor or a Post-Graduate, not both. Post-Graduate specializes further into Master and Doctorate. Each leaf can join its own relationships, so Bachelors register for Projects and Post-Graduates register for a Thesis.*

## Aggregation

ISA relates entity sets to entity sets. Aggregation handles a different need: relating a relationship to an entity, by treating a whole relationship as if it were one entity set.

**Aggregation.** A mechanism that treats a relationship set together with its participating entity sets as a single higher-level entity set, so the bundle can itself participate in another relationship.

Aggregation is needed when a relationship must involve a relationship. *Departments sponsor projects through `Sponsors`, and an employee must monitor each sponsorship.* Modeling this as a ternary relationship among Projects, Departments, and Employees would lose the fact that monitoring applies to the sponsorship itself, not to an independent triple. Enclosing `Sponsors` in a dashed box turns it into an entity set that then participates in `Monitors`.

## Design Choices

A correct ER schema is rarely unique. The recurring decisions are whether a concept is an entity or an attribute, whether it is an entity or a relationship, and whether a relationship should be binary, ternary, or replaced by aggregation. Each answer depends on the data's semantics and the queries the application must support.

The entity-versus-attribute choice turns on structure and multiplicity, because attributes in the basic ER model are atomic and single-valued. An *address* must become its own entity if an employee can have several addresses, or if the address has internal structure such as city, street, and zip that the application needs to query. The same reasoning applies to relationship attributes: if `Works_In` records a period with `from` and `to`, an employee can hold only one period; to record several periods the time must be promoted into a separate `Duration` entity linked by a new relationship.

The entity-versus-relationship choice turns on identity: if a concept has its own identity or participates in other relationships, make it an entity rather than a relationship. The binary-versus-ternary choice turns on decomposability: prefer binary relationships when a ternary one can be split into binaries without losing information, and keep the ternary only when some combination of pairs does not imply the triple.

Finally, the ER model captures a great deal of semantics directly, including key constraints, participation constraints, weak entities, ISA hierarchies, and aggregation, but not everything. A rule such as *a manager must also be an employee of the department they manage* cannot be expressed in an ER diagram and has to be enforced by the application or by database-level integrity constraints.
