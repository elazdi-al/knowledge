## Reaching a Host Behind a NAT

A NAT creates entries only from outbound traffic, so a host behind it can start a conversation but cannot receive one first.

Port forwarding fixes this for a server, if the server knows the NAT's public address and can advertise it.

**UPnP (Universal Plug and Play).** A protocol a LAN host uses to make its NAT set up port forwarding and to learn the NAT's public address.

UPnP offers three requests.

- `AddPortMapping`: the host asks for a *specific* public port. The NAT sets it up or reports a conflict.
- `AddAnyPortMapping`: the host asks for *any* public port.
- `GetExternalIPAddress`: the host learns the NAT's public address.

UPnP authenticates nobody: any program on any LAN device can open a port. Many NATs disable it, carrier-grade NATs rarely offer it, and browsers do not use it.

**STUN (Session Traversal Utilities for NAT).** A protocol in which a public server tells a host the public IP address and port its request came from: the mapping the host's NAT created on the way out.

That mapping points toward the STUN server. Whether another peer can use it depends on how the NAT maps and filters.

A NAT does two jobs. As a **translator**, it maps an internal IP:port to a NAT IP:port, one NAT table entry per mapping. As a **filter**, it decides which outside senders may send in. The filtering router of an IPv6 home is a filter alone.

An **endpoint-independent** mapping gives an internal IP:port one NAT port toward every peer:

$$
\text{internal IP:port} \rightarrow \text{NAT IP:port}
$$

An **endpoint-dependent** mapping gives it a new NAT port for each destination:

$$
(\text{internal IP:port},\ \text{destination IP:port}) \rightarrow \text{NAT IP:port}
$$

The filter admits any outside host, only the IP addresses the internal host has contacted, or only the exact IP:port pairs it has contacted.

*The mapping decides which public address a peer must aim at; the filter decides whether the NAT lets that peer in.*

| NAT type | Mapping | Who can send in? |
|---|---|---|
| Full cone | endpoint-independent | any outside host |
| Address-restricted cone | endpoint-independent | only the **IP addresses** contacted |
| Port-restricted cone | endpoint-independent | only the **IP:port pairs** contacted |
| Symmetric | endpoint-dependent | only the **IP:port pairs** contacted |

Each row is harder to traverse than the one above.

ICMP packets carry no port. Some NATs drop ICMP, and others use the **ICMP echo request identifier** of `ping` in place of the port.

**Example 1. How many hosts can a NAT serve?**

*A NAT with one public address serves the private block `10.0.0.0/8`. How many internal hosts can it serve at most?*

*Not the $2^{24}$ addresses of the /8. Each NAT table entry takes one TCP or UDP port, and each protocol has 16-bit ports, so the NAT holds fewer than $2 \times 2^{16}$ entries (minus reserved and blocked ports). That is also the host limit, reached when each host has a single connection.*

The hard case is two hosts that are *both* behind NATs (e.g. a browser video call exchanging UDP media). Neither can receive an unsolicited packet.

**Signalling channel.** An out-of-band path between the two peers, such as the call service's web server. The peers use it to exchange the addresses STUN reported.

```text
A   192.168.1.10:5000   behind NAT A, public address 198.51.100.1
B   10.0.0.7:6000       behind NAT B, public address 198.51.100.2
S   203.0.113.9:3478    STUN server
```

Whatever the NAT types, the call starts the same way.

1. Each peer sends a STUN request to S and learns its public address and port.
2. Each peer tells the other, over the signalling channel, the address STUN reported.
3. Each peer sends packets to the address the other reported.

**Example 2. Two full cone NATs.**

*NAT A maps A to `198.51.100.1:40001` and NAT B maps B to `198.51.100.2:50001`, toward every peer. A sends to `198.51.100.2:50001` and B to `198.51.100.1:40001`. Do the packets arrive?*

*Yes. The port STUN reported is the port the peer reaches, and the filter lets any host in.*

**Example 3. Two symmetric NATs.**

*Same call, but nothing arrives at either end. The NAT tables after step 3 show why.*

| NAT | Internal IP:port | Destination | NAT IP:port |
|---|---|---|---|
| A | `192.168.1.10:5000` | S, `203.0.113.9:3478` | `198.51.100.1:40001` |
| A | `192.168.1.10:5000` | B, `198.51.100.2:50001` | `198.51.100.1:40002` |
| B | `10.0.0.7:6000` | S, `203.0.113.9:3478` | `198.51.100.2:50001` |
| B | `10.0.0.7:6000` | A, `198.51.100.1:40001` | `198.51.100.2:50002` |

*B aims at port 40001, but that entry is bound to S, so NAT A drops the packet. The entry toward B is port 40002, and nobody tells B about it. The same happens the other way. STUN reported the one mapping neither peer needs, and a second STUN server only reports another useless one. TCP fails the same way.*

**Example 4. Two port-restricted cone NATs.**

*The mappings are endpoint-independent again: NAT A keeps port 40001 toward every destination, and NAT B keeps 50001. But each filter admits only the IP:port pairs its host has contacted, so far only S. Does the call work?*

*Yes, after one more step. Each peer was told the right port, but the filter is still closed. Opening it costs one outbound packet on each side.*

**Hole punching.** A technique in which both peers send to each other's STUN-learned address at roughly the same time, so that each outbound packet opens the sender's NAT filter for the other peer.

After the STUN requests and the address exchange, hole punching takes four steps.

1. Both peers send a packet to the other's reported address.
2. Each far NAT drops the packet, since its host has not contacted the sender yet.
3. Each packet still opens its sender's *own* NAT filter for the peer.
4. The retransmissions get through in both directions.

*Neither side can receive, but both can send, and sending creates permission to receive.*

<HolePunchingSchema />

Hole punching needs the signalling channel to coordinate, and its first packets are lost by design. It also works for an address-restricted cone, whose filter is looser. Two full cone NATs need no punching.

Hole punching often fails behind symmetric NATs, yet they persist, mostly in carrier-grade NATs. They combine easily with a per-flow stateful firewall and simplify load balancing, since a cluster of symmetric NATs shares no state. Guessing their next port is unreliable, which leaves a relay.

**TURN (Traversal Using Relays around NAT).** A public server that relays the media: each peer sends to the relay, which forwards to the other peer. TURN works behind any NAT, at the price of an indirect path.

**ICE (Interactive Connectivity Establishment).** An algorithm that gathers every candidate address of a peer, checks them all, and prefers direct paths to relayed ones. The candidates are the host address (the peer's own interface), the STUN-learned address and a TURN-relayed address.

IPv6 avoids the problem. Each host knows its global address, and the only obstacle left is the filtering router of an IPv6 home, which hole punching opens.

## NAT64 and DNS64

Dual stack is one way to bridge IPv4 and IPv6. Translation is the other.

**NAT64.** A box at the boundary between an IPv6 network and the IPv4 internet that translates packet headers, so that an IPv6-only client (client6) can reach an IPv4-only server (server4).

NAT64 translates the two addresses differently.

- **Client's address.** The IPv6 address becomes an IPv4 address from a pool, recorded in a classic NAT table (stateful).
- **Server's address.** An IPv6 address with an IPv4 address embedded in it becomes that IPv4 address, by arithmetic alone (stateless).

**IPv4-embedded IPv6 address.** A 96-bit prefix followed by a 32-bit IPv4 address, which makes every IPv4 server addressable from IPv6. The prefix is the well-known `64:ff9b::/96` or a /96 from the network's own block (e.g. `2001:db8:64::/96`).

*Embedding writes the IPv4 address's four bytes in hex: `203.0.113.5` is `cb.00.71.05`, so server4 becomes `64:ff9b::cb00:7105`. NAT64 recovers `203.0.113.5` by dropping the prefix.*

The client knows only the server's name, so it still has to learn that address.

**DNS64.** A DNS resolver that, when a name has only an IPv4 (A) record, synthesizes an AAAA record by embedding that IPv4 address into the NAT64 prefix. A name with a real AAAA record gets it back unchanged.

For a name with only an A record, resolution takes four steps.

1. The client asks its resolver for the AAAA record of `example.net`.
2. DNS64 finds only an A record, synthesizes `64:ff9b::cb00:7105` and returns it.
3. The client connects to that IPv6 address like any other.
4. Routing carries the packets to the NAT64 box, which translates them. The client never learns that IPv4 was involved.

<Nat64Schema />

| Packet | Source | Destination |
|---|---|---|
| IPv6, client6 to NAT64 | `2001:db8:1234:1::d` (client6) | `64:ff9b::cb00:7105` |
| IPv4, NAT64 to server4 | a pool address, recorded in the NAT table (stateful) | `203.0.113.5`, the prefix dropped (stateless) |

DNS64 steers traffic toward the translator by choosing which address to return, as content delivery networks and load balancers do.

## Configuring an Interface

Every exchange so far assumed configured hosts.

A host's IP interface needs four items.

1. its IP address,
2. its subnet mask,
3. the IP address of its default gateway,
4. the IP address of a DNS server.

They are set by hand or automatically: in IPv4 by DHCP, in IPv6 by DHCP or by SLAAC.

A router's interface toward its provider is configured by **PPP** (Point-to-Point Protocol), which configures telecom lines such as ADSL, or in IPv6 also by DHCP with prefix delegation.

**DHCP (Dynamic Host Configuration Protocol).** A protocol in which a server hands hosts their configuration, in IPv4 all four items. **Stateful** DHCP also remembers which address went to which host.

The DHCP exchange is a two-phase commit, with four messages in IPv4.

1. The host discovers a DHCP server: **DISCOVER**.
2. The server returns an offer: **OFFER**.
3. The host commits to the offer: **REQUEST**.
4. The server confirms the commitment: **ACK**.

**Lease.** The server's record binding an address to a client after the ACK. It is valid for a limited time, and the client renews it to keep the address.

The host does not know the server's address, so it broadcasts (IPv4) or multicasts (IPv6).

An IPv4 DISCOVER travels in UDP from port 68 to port 67 and carries the client's MAC address. Its source is `0.0.0.0`, since the host has no address yet, and its destination `255.255.255.255`, everyone on the LAN.

A broadcast never leaves the LAN, so the server sits on the same LAN or the gateway relays the messages.

**DHCP relay.** A gateway that picks up its LAN's DHCP messages and forwards them to a DHCP server in another network, so that one server can serve many subnets.

<DhcpRelaySchema />

Without DHCP, IPv4 has a last resort.

**IPv4 self-autoconfiguration.** An IPv4 host with no manual configuration and no DHCP server gives itself a link-local address at boot.

The host takes two steps.

1. It picks an address *at random* from the link-local block `169.254.0.0/16`.
2. It runs an **address duplication test**: it broadcasts an **ARP probe**, a "who has this address?" request sent from `0.0.0.0`, and keeps the address if nobody answers.

Self-autoconfiguration lets hosts talk on unmanaged networks without a router, and is not meant for general use. Windows implements it; Linux does not always.

## Autoconfiguration in IPv6

IPv6 can configure a host without a DHCP server.

**SLAAC (Stateless Address AutoConfiguration).** An IPv6 host builds its own addresses, first a link-local one and then a global one from a prefix announced by a router, with no server keeping state.

1. **Link-local address.** The host appends a 64-bit host part to `fe80::/64`.
2. **Address duplication test.** The host sends a query for the address to its **solicited-node multicast address**: the prefix `ff02::1:ff00:0/104` followed by the last 24 bits of the host part.
3. **Global address.** The host sends a **router solicitation (RS)** to all routers, `ff02::2`. A router answers with a **router advertisement (RA)** carrying a /64 prefix, and the host appends its host part to it. SLAAC ignores a prefix that is not 64 bits long.

*SLAAC always gives a link-local address, and a global one only once an RA arrives.*

The host part comes in five kinds.

- **Manual.** Set by hand (e.g. `::1`).
- **Modified EUI-64.** Derived from the MAC address.
- **Temporary.** Random and short-lived.
- **RFC 7217.** Random-looking but fixed for each subnet.
- **CGA.** Derived from a hash of the host's public key.

**Modified EUI-64.** The 64-bit host part derived from a 48-bit MAC address. Split the MAC address into its two 3-byte halves, insert `ff:fe` between them, and flip the second-lowest bit of the first byte.

**Example 5. A MAC-derived address.**

*The EPFL host lrcmac4 has MAC address `08:00:20:78:30:f9`. Which addresses does SLAAC give it?*

```text
MAC address          08:00:20:78:30:f9
insert ff:fe         08:00:20:ff:fe:78:30:f9
flip the bit         0a:00:20:ff:fe:78:30:f9
link-local address   fe80::a00:20ff:fe78:30f9
solicited node       ff02::1:ff78:30f9
global address       2001:620:618:1ad:a00:20ff:fe78:30f9
```

*Flipping the bit turns `08` = 0000 1000 into 0000 1010 = `0a`. The global address uses the prefix `2001:620:618:1ad::/64` from an RA. The MAC address stays visible in every address of lrcmac4.*

SLAAC gives no DNS server address, which a host gets in one of two ways.

- **Stateless DHCP.** A DHCP server that keeps no lease state and gives the DNS server's address to every host that asks.
- **RA option** (RFC 8106). The router adds the DNS server's address to its RA.

Routers also send RAs unasked, periodically, to all nodes at `ff02::1`. The router that sends an RA becomes the host's default gateway, so one RA covers all four items.

A MAC-derived host part is the same on every network the host joins, so anyone who collects addresses can track the host as it moves. Two kinds of host part prevent this tracking.

**Temporary address.** An address with a random host part and a limited lifetime.

A temporary address passes through four states:

1. **tentative**, until the duplication test succeeds;
2. **preferred**, in normal use, until the preferred timer expires;
3. **deprecated**, no longer used to start new TCP connections, until the validity timer expires;
4. **invalid**.

**RFC 7217 address ("secure autoconf").** An address whose host part is a hash of the interface, the subnet prefix and a secret key chosen when the operating system is installed:

$$
\text{host part} = \text{hash}(\text{interface id},\ \text{subnet prefix},\ \text{secret key})
$$

An RFC 7217 address stays the same on one subnet and changes unpredictably between subnets. A temporary address instead changes over time on the same subnet.

An interface typically holds both: the RFC 7217 address is the stable one, the temporary address the private one, and source address selection picks between them.

An IPv6 home's devices configure themselves by SLAAC, so the home router needs a prefix to advertise. The provider hands it one by DHCP.

**DHCP with prefix delegation.** DHCP in which the provider's server, the **delegating router**, gives the home router a whole prefix instead of one address. If the link between them uses a prefix inside the delegated block, that prefix is excluded (RFC 6603).

**Example 6. A delegated /60.**

*Swisscom delegates `2004:aaaa:bbbb:cc00::/60` to home router R0. The /60 holds $2^{64-60} = 16$ /64 prefixes, `cc00` to `cc0f` in the fourth hextet. The ISP link uses `cc01`, which is excluded, and R0 advertises `cc02` on the home LAN, leaving 14 free.*

## Hop Limit and Traceroute

Forwarding tables change when a link fails or routes are recomputed, and the change reaches routers at different times.

**Transient loop.** Two routers forwarding a destination's packets to each other while their tables disagree. A packet caught in it bounces back and forth. When propagation is short compared to transmission, a few such packets keep the link busy and congest it.

**Hop Limit (IPv6) / Time to Live (IPv4).** An 8-bit field (0 to 255) in every IP packet, decremented at every IP hop. It exists to kill packets caught in transient loops.

- **Who decrements.** Every router and every NAT decrements HL/TTL. Switches do *not*.
- **Initial value.** Usually 64 at the source.
- **Expiry.** When HL/TTL reaches 0, the packet is discarded.

*Hop limit counts routers, not links: a device that only switches frames inside a LAN never looks at it.*

**Example 7. A packet with hop limit 1.**

*A host sends a packet with Hop Limit = 1. Is the packet invalid?*

*No. A router cannot forward it, since decrementing gives 0, but a switch can, since it never reads the IP header. Sources set HL = 1 to keep a packet inside the LAN.*

The same counter can map a path.

**Traceroute.** A tool that discovers the routers on the path to a destination by making each of them, in turn, report an expired packet.

1. The source sends a series of UDP probes to the destination, with TTL = 1, then 2, then 3, and so on.
2. The router where a probe's TTL expires discards it and sends an **ICMP error message** (time exceeded) back to the source.
3. The source learns that router's IP address from the source address of the error message, so the probe with TTL $n$ reveals the $n$-th router.

<TracerouteSchema />

The last probe reaches the destination. For a UDP probe, it answers with an ICMP error saying that no application listens on that port, and the trace ends.

Linux and macOS send UDP probes by default. `traceroute -I` and Windows' `tracert` send ICMP echo requests instead.

The tool looks up router names by reverse DNS (address to name). A `*` means that no reply arrived for that probe.

**Example 8. Reading a traceroute.**

*`tracert` from an EPFL host to Google over IPv6. Each line is one TTL value: the round-trip times of three probes, then the router that answered.*

```text
Tracing route to www.google.com [2a00:1450:4008:800::1012]
over a maximum of 30 hops:

  2    <1 ms    <1 ms    <1 ms  cv-gigado-v100.epfl.ch [2001:620:618:164:1:80b2:6412:1]
  3    <1 ms    <1 ms    <1 ms  c6-ext-v200.epfl.ch [2001:620:618:1c8:1:80b2:c801:1]
```

| Hops | Network | Note |
|---|---|---|
| 1 to 3 | EPFL | inside `2001:620:618::/48` |

Each probe is routed independently, so the output approximates the path well but does not guarantee it.*

Besides hop limit and the addresses, the IP header carries these fields.

| Field (IPv4 / IPv6) | Content |
|---|---|
| Type of Service / Traffic Class | 6 bits of **Differentiated Services**, roughly a priority (e.g. for voice over IP), honoured only inside one administration; 2 bits of **Explicit Congestion Notification** |
| Total Length / Payload Length | size in bytes, *with* the header in IPv4, *without* it in IPv6; at most 65 535, in practice limited by the link's MTU |
| Header Checksum (IPv4 only) | detects bit errors in the header; IPv6 drops it and relies on the data link and network hardware to detect errors |

**MTU (Maximum Transmission Unit).** The largest packet a data link layer carries in one frame: 1500 bytes for Ethernet.

Besides 6 (TCP), 17 (UDP), 1 (ICMP) and 58 (ICMPv6), the Protocol / Next Header field can name tunnels and security protocols.

| Protocol / Next Header | Upper layer |
|---|---|
| 4 | IPv4, encapsulated in IP (a tunnel) |
| 41 | IPv6, encapsulated in IP (a tunnel) |
| 50 | ESP, an encrypted payload |
| 51 | AH, an authentication header |

## From IP Address to MAC Address

Within a subnet, the MAC layer moves the data, so every frame needs the MAC address of the neighbour it is sent to.

**MAC address resolution.** Finding the MAC address of an IP address in the same subnet.

Host A has a packet for neighbour B, the destination or the next hop toward it (e.g. the default gateway), and knows only B's IP address. A broadcasts (IPv4) or multicasts (IPv6) "who has B's IP address?" on the LAN, and B answers with its MAC address.

*Resolve the neighbour the frame goes to, never the far destination: MAC addresses are local, so only a neighbour's is needed.*

**NDP (Neighbor Discovery Protocol).** IPv6's address-resolution protocol. Its messages are ICMPv6 packets, carried inside IPv6 packets with next header 58 (`0x3a`).

- **Neighbor Solicitation (NS).** The question "who has IP address B?".
- **Neighbor Advertisement (NA).** The answer, giving B's MAC address.

SLAAC's router solicitations and advertisements are NDP messages too, and its duplication test is an NS for the host's own tentative address.

**Neighbor cache.** A host's table of the IP address to MAC address mappings learned by address resolution. Entries expire after a configurable idle time, which feedback from higher-layer protocols can extend.

A resolves B on one LAN.

```text
A   2001:620:618:1a6:1:80b2:f01:1   MAC 08:00:20:71:0d:d4
B   2001:620:618:1a6:1:80b2:f66:1   MAC 00:00:d0:b3:d2:8d
```

| Step | Message | Destination IP | Destination MAC |
|---|---|---|---|
| 1 | A's NS: who has B's address? | `ff02::1:ff66:1`, B's solicited node | `33:33:ff:66:00:01` |
| 2 | B's NA: B's MAC address | A's address | `08:00:20:71:0d:d4` |
| 3 | A's data, once B is in its neighbor cache | B's address | `00:00:d0:b3:d2:8d` |

The solicited-node address keeps the NS from bothering the whole LAN.

Every host joins the solicited-node group of each of its addresses. A packet to the group reaches the hosts whose addresses share its last 24 bits, normally only the target.

The frame's destination MAC is `33:33` followed by the last 32 bits of the destination IP, so every other host drops the frame on its MAC address alone. IPv4 has no solicited-node addresses and broadcasts instead.

<SolicitedNodeSchema />

**Ethertype.** The field of the MAC frame header that names the protocol the frame carries: `0x86dd` for IPv6, `0x0800` for IPv4.

**Example 9. A captured NS.**

```text

ETHER:  Destination = 33:33:ff:01:00:01
ETHER:  Source = 3c:07:54:3e:ab:f2
ETHER:  Ethertype = 0x86dd
IP:     Version = 6
IP:     Traffic class = 0x00000000
IP:     Flowlabel = 0x00000000
IP:     Payload length = 32
IP:     NextHeader = 58
IP:     Hop limit = 255
IP:     Source address = 2001:620:618:197:1:80b2:97c0:1
IP:     Destination address = ff02::1:ff01:1
ICMPv6: Type = 135

ICMPv6: Checksum = 0xb199 [correct]
ICMPv6: Reserved = 0

```

*ICMPv6 type 135 is an NS. The target ends in `9701:1`, so the destination IP is `ff02::1:ff01:1` and the destination MAC `33:33:ff:01:00:01`. The frame is $14 + 40 + 32 = 86$ bytes: Ethernet header, IPv6 header, ICMPv6 payload. The target is hop 1 of Example 8, the router of `2001:620:618:197::/64`, and the source sits in the same /64: a host resolving its router.*

**ARP (Address Resolution Protocol).** IPv4's address-resolution protocol.

ARP differs from NDP in three ways.

- **Terminology.** The NS and NA are called **ARP request** and **ARP reply**, and the neighbor cache is called the **ARP table**.
- **Protocol type.** ARP packets are not ICMP packets and are not even carried in IP packets. They sit directly in the MAC frame, with Ethertype `0x0806`.
- **Reachability.** The ARP request is broadcast to all nodes of the LAN, not multicast.

**Example 10. A captured ARP request.**

```text
Ethernet II
    Destination: ff:ff:ff:ff:ff:ff (ff:ff:ff:ff:ff:ff)
    Source: 00:03:93:a3:83:3a (Apple_a3:83:3a)
    Type: ARP (0x0806)
    Trailer: 000000000000000000000000000000000...
Address Resolution Protocol (request)
    Hardware type: Ethernet (0x0001)
    Protocol type: IP (0x0800)
    Hardware size: 6
    Protocol size: 4
    Opcode: request (0x0001)
    Sender MAC address: 00:03:93:a3:83:3a (Apple_a3:83:3a)
    Sender IP address: 129.88.38.135 (129.88.38.135)
    Target MAC address: 00:00:00:00:00:00 (00:00:00_00:00:00)
    Target IP address: 129.88.38.254 (129.88.38.254)
```

*The frame goes to the broadcast MAC address `ff:ff:ff:ff:ff:ff`, with type ARP, not IP. Inside, protocol type `IP (0x0800)` names the protocol being resolved, IPv4. The target MAC address is all zeros: it is what the request asks for.*

The ARP probe of IPv4 self-autoconfiguration is such a request, sent from `0.0.0.0`.

On Linux, `ip route show` gives the gateway's IP address, and `arp -a` lists the ARP table.

**Example 11. M1 just boots.**

*M1 to M9 are MAC addresses. M1 has just booted and sends a packet to M3 at `q.h1`. Does M1 resolve `q.h1` or `p.1`?*

*`p.1`. M3 is outside M1's subnet, so the frame goes to the default gateway, whose IP address M1 knows from its configuration but whose MAC address it does not. The frame reaches M9 still carrying destination IP `q.h1`, and the router then resolves `q.h1` on subnet q.*

## Securing Address Resolution

ARP and NDP trust whoever answers, and nothing authenticates the answer.

**ARP spoofing.** An attack in which a forged ARP reply or NA makes a victim map another host's IP address to the attacker's MAC address.

1. The attacker sees A's request for B's MAC address (easier in IPv4, where ARP requests are broadcast to everyone).
2. The attacker sends a bogus ARP reply or NA carrying its own MAC address.
3. If the bogus answer arrives before B's, A maps B's IP address to the attacker's MAC address and sends B's traffic to the attacker.

**Rogue RA.** A router advertisement from a host that is not a legitimate router. A single rogue RA makes its sender everyone's default gateway on the link. Most rogue RAs are accidental, from misconfigured virtual machine hosts or Windows internet connection sharing.

ARP spoofing and rogue RAs both open the way to a **man-in-the-middle attack**: the attacker receives the victims' traffic, can read or alter it, and passes it on so that nobody notices.

Mitigations sit in the LAN switch or the WiFi base station, which sees every frame.

- **DHCP snooping.** The switch or WiFi base station observes all DHCP traffic and remembers the IP address ↔ MAC address mappings the DHCP server hands out. Two defences build on these mappings:
  - **Dynamic ARP inspection.** The switch filters all ARP (or NDP) traffic and allows only valid answers.
  - **ARP proxy.** The WiFi base station answers ARP requests itself.
- **RA guard** (RFC 6105). The switch drops RAs arriving on ports where no router exists.

These defences are deployed in enterprise networks, rarely at home or on WiFi base stations.

The cryptographic alternative makes the answer itself verifiable.

**Public-key cryptography.** Each party holds two keys: a public key $P$, shared with everyone, and a private key $p$, kept secret. What one key encrypts, only the other decrypts.

**Digital signature.** $p(m)$, the message $m$ encrypted with the sender's private key and sent along with $m$. The receiver decrypts it with $P$ and compares the result with $m$: a match proves that the owner of $p$ signed $m$, and a mismatch marks $m$ as forged.

**SEND (Secure Neighbor Discovery).** NDP in which each address is bound to its owner's public key and each NA is signed, which makes NDP spoofing impossible.

**Cryptographically generated address (CGA).** An address whose host part is a hash of the owner's public key, the fifth kind of SLAAC host part:

$$
\text{host part} \approx \text{hash}(P,\ \text{IPv6 prefix},\ \text{CGA parameters})
$$

SEND takes four steps.

1. B creates an RSA key pair, private key $p$ and public key $P$.
2. B computes its CGA from $P$, the IPv6 prefix and other parameters such as counters. The hash binds B's IP address to $P$.
3. B puts $P$ and the CGA parameters in its NA and signs the NA with $p$.
4. A recomputes the hash to check that the CGA matches $P$, and checks the signature with $P$.

NAs can also carry **nonces**, values used only once, so that an attacker cannot replay an old valid NA.

Anyone can compute a CGA for a public key $P$. Only the owner of $p$ can sign for it.

SEND needs a strong hash function (SHA-1 is currently used) and possibly a trusted certification authority (e.g. RPKI), so it is not widespread yet.
