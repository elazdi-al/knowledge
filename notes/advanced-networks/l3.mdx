## Reaching a Host Behind a NAT

A NAT creates its table entries from outbound traffic, so a host behind it can start a conversation but cannot be reached before it does. Port forwarding fixes this for a server, provided the server knows the NAT's public address and can advertise it.

**UPnP (Universal Plug and Play).** A protocol a LAN host uses to make its NAT set up port forwarding automatically and to learn the NAT's public address.

UPnP offers three requests.

- `AddPortMapping`: the host asks for a *specific* public port. The NAT sets it up or reports a conflict.
- `AddAnyPortMapping`: the host asks for *any* public port.
- `GetExternalIPAddress`: the host learns the NAT's public address.

Not every NAT enables UPnP. Where it is enabled, it accepts requests from LAN hosts without authenticating them, so any program on any device can open a port. Browsers do not use UPnP, and carrier-grade NATs typically do not offer it.

**STUN (Session Traversal Utilities for NAT).** A protocol in which a public server tells a host which public IP address and port its packets appear to come from. The host sends a request, and the server replies with the source IP address and port it observed on that request. That pair is the mapping the host's NAT created on the way out.

A STUN server returns the mapping it observed, which is the mapping *toward the STUN server*. Whether another peer can reach the host through that mapping depends on how the NAT builds mappings.

A NAT does two separable jobs. As a **translator**, it maps an internal (IP address, port) pair, written IP:port, to a NAT IP:port. Each such mapping is an entry of its NAT table. As a **filter**, it decides which external senders may send packets in. The filtering router of an IPv6 home is a filter alone.

NAT types differ in how they map and how they filter.

- **Mapping.** Whether the NAT port depends on the external peer. An *endpoint-independent* mapping gives an internal IP:port one NAT port toward every peer. An *endpoint-dependent* mapping gives it a new NAT port for each destination.
- **Inbound filtering.** Who may send in: any external host, only the IP addresses the internal host has contacted, or only the exact IP:port pairs it has contacted.

*The mapping decides which public address a peer must aim at; the filter decides whether the NAT lets that peer in.*

| NAT type | Mapping | Inbound filtering: who can send in? |
|---|---|---|
| Full cone | endpoint-independent | any external host |
| Address-restricted cone | endpoint-independent | only the **IP addresses** the internal host has contacted |
| Port-restricted cone | endpoint-independent | only the **IP:port pairs** the internal host has contacted |
| Symmetric | endpoint-dependent: one mapping per destination IP:port | only the **IP:port pairs** the internal host has contacted |

Each row is harder to traverse than the one above it. Where UPnP is available, it can set the filtering rule too.

**Full cone NAT.** A NAT that maps every packet from one internal IP:port to the same NAT IP:port. *Any* external host can reach the internal host by sending to that NAT IP:port.

$$
\text{internal IP:port} \rightarrow \text{NAT IP:port}
$$

**Symmetric NAT.** A NAT that maps every packet from one internal IP:port *to one destination IP:port* to the same NAT IP:port. The same source sending to a different destination gets a different mapping, so one internal IP:port may hold several NAT ports. *Only* the external host that received a packet can send one back.

$$
(\text{internal IP:port},\ \text{destination IP:port}) \rightarrow \text{NAT IP:port}
$$

ICMP packets, such as the echo requests of `ping`, carry no port number. Some NATs do not support ICMP. Others use the **ICMP echo request identifier** in place of the port.

The hard case is two hosts that are *both* behind NATs. A and B want to start a video call in their browsers (e.g. Teams) and exchange UDP media. Neither can receive an unsolicited packet, so they first need a path both can reach.

**Signalling channel.** An out-of-band path between the two peers, such as the call service's web server acting as a relay. The peers use it to exchange the addresses STUN reported to each.

Let A be `192.168.1.10:5000` behind NAT A (public address `198.51.100.1`), B be `10.0.0.7:6000` behind NAT B (public `198.51.100.2`), and S the STUN server `203.0.113.9:3478`.

Whatever the NAT types, the call starts the same way.

1. Each peer sends a STUN request to S and learns its public address and port.
2. Each peer tells the other, over the signalling channel, the address STUN reported.
3. Each peer sends packets to the address the other reported.

**Example 1. Two full cone NATs.**

*NAT A maps `192.168.1.10:5000` to `198.51.100.1:40001` and NAT B maps `10.0.0.7:6000` to `198.51.100.2:50001`, with no destination column: one NAT port toward every peer. A sends to `198.51.100.2:50001` and B to `198.51.100.1:40001`. Do the packets arrive? Yes. The port STUN reported is the port the peer reaches, and any external host may use it, so every inbound packet matches a NAT table entry and is forwarded inside.*

**Example 2. Two symmetric NATs.**

*Same call, but nothing arrives at either end. The NAT tables after step 3 show why.*

| NAT | Entry created by | Internal IP:port | Destination | NAT IP:port |
|---|---|---|---|---|
| A | STUN request | `192.168.1.10:5000` | `203.0.113.9:3478` (S) | `198.51.100.1:40001` |
| A | packet to B | `192.168.1.10:5000` | `198.51.100.2:50001` (B) | `198.51.100.1:40002` |
| B | STUN request | `10.0.0.7:6000` | `203.0.113.9:3478` (S) | `198.51.100.2:50001` |
| B | packet to A | `10.0.0.7:6000` | `198.51.100.1:40001` (A) | `198.51.100.2:50002` |

*B aims at port 40001, but that entry is bound to S, not to B, so NAT A drops the packet. The entry that would reach A is port 40002, and nothing tells B about it. Symmetrically, A aims at port 50001, bound to S, while the port that would reach B is 50002. STUN was not wrong: it reported the mapping toward S, the one mapping neither peer needs. A second STUN server would only report a second useless mapping. The packets die at the NATs, before either host's operating system sees them. TCP would fare no better, since its mappings behave the same way.*

**Example 3. Two port-restricted cone NATs.**

*The mappings are endpoint-independent again: NAT A maps `192.168.1.10:5000` to `198.51.100.1:40001` toward every destination, and NAT B maps `10.0.0.7:6000` to `198.51.100.2:50001`. But each filter admits only the IP:port pairs its host has contacted, and so far that is S alone. Does the call work? Yes, but learning the correct public IP:port is necessary, not sufficient. A port-restricted cone shares its filter with a symmetric NAT but not its mapping, so the port a host opens by sending is the port its peer was told about. The filter is still closed, and opening it costs one outbound packet on each side.*

**Hole punching.** A technique in which both peers send to each other's STUN-learned address at roughly the same time, so that each outbound packet opens the sender's NAT filter for the other peer.

After the STUN requests and the address exchange, hole punching takes four steps.

1. Both peers send a packet to the other's reported address at roughly the same time.
2. NAT B drops A's packet: B has not sent to A yet, so NAT B holds no permission for A. NAT A drops B's packet for the same reason.
3. But each packet installed a permission on its sender's *own* NAT: NAT A now accepts packets from B, and NAT B from A.
4. The retransmissions get through, and both directions are open.

*Neither side can receive, but both can send, and sending creates permission to receive.*

<HolePunchingSchema />

The hole is punched from the inside outward, by both sides at once. That is why hole punching needs an out-of-band channel to coordinate, and why the first packets are expected to be lost. The same procedure works for an address-restricted cone, whose filter is looser. Two full cone NATs need no punching.

Hole punching often fails behind symmetric NATs, yet symmetric NATs persist. They are easy to combine with a per-flow stateful firewall, they can simplify load balancing (a cluster of NATs then avoids sharing state), and they are common in carrier-grade NATs, where UPnP is typically unavailable. For a video or SIP phone call through them, guessing the next port is unreliable, which leaves a relay.

**TURN (Traversal Using Relays around NAT).** A public server that relays the media: each peer sends to the relay, which forwards to the other peer. TURN works behind any NAT, at the price of an indirect path.

**ICE (Interactive Connectivity Establishment).** An algorithm that gathers every candidate address of a peer, checks them all, and prefers direct paths to relayed ones. The candidates are the host address (the peer's own interface), the STUN-learned address and a TURN-relayed address.

The best escape is IPv6. Without translation, each host knows its global address, and the only obstacle left is at most the filtering router of an IPv6 home, which hole punching can open.

**Example 4. How many hosts can a NAT serve?**

*An internal subnet uses the private block `10.0.0.0/8` behind a NAT with one public address, `130.104.228.200`. Hosts A (`10.0.10.11`) and B (`10.0.10.10`) both send from UDP port 1029, and the NAT maps them to ports 3441 and 3442. What is the maximum number of internal hosts? Not $2^8$, and not the $2^{24}$ addresses of the /8. The NAT creates entries on the fly, choosing ports that avoid collisions, so it holds at most as many entries as it has usable TCP and UDP port numbers (those neither reserved nor blocked by a firewall). TCP and UDP each have 16-bit ports, so the NAT holds fewer than $2 \times 2^{16} = 2 \times 65\,536$ entries, far below $2^{24}$. That bound is also the maximum number of hosts, reached when each host has a single TCP or UDP connection to the outside.*

## NAT64 and DNS64

IPv4 and IPv6 are incompatible. Dual stack is one workaround, and translation is the other.

**NAT64.** A box at the boundary between an IPv6 network and the IPv4 internet that translates packet headers, so that an IPv6-only client (client6) can reach an IPv4-only server (server4).

NAT64 translates the two addresses differently.

- **Client's address.** The IPv6 address becomes an IPv4 address from a pool, recorded in a classic NAT table (stateful).
- **Server's address.** An IPv6 address with an IPv4 address embedded in it becomes that IPv4 address, by arithmetic alone (stateless).

**IPv4-embedded IPv6 address.** An IPv6 address made by appending a 32-bit IPv4 address to a 96-bit prefix, which makes every IPv4 server addressable from IPv6. The prefix is the well-known `64:ff9b::/96`, or a /96 taken from the network's own prefix, such as `2001:db8:64::/96` for a provider holding `2001:db8:64::/48`.

*Embedding writes the IPv4 address's four bytes in hex: `203.0.113.5` is `cb.00.71.05`, so server4 becomes `64:ff9b::cb00:7105`, or `2001:db8:64::cb00:7105` with the provider's prefix. NAT64 recovers `203.0.113.5` by dropping the prefix.*

The client knows only the server's name, so it still has to learn that address.

**DNS64.** A DNS resolver that, when a name has only an IPv4 (A) record, synthesizes an AAAA record by embedding that IPv4 address into the NAT64 prefix. A name with a real AAAA record gets it back unchanged.

For a name with only an A record, resolution takes four steps.

1. The client asks its resolver for the AAAA record of `example.net`.
2. DNS64 finds only an A record, synthesizes `64:ff9b::cb00:7105` (or `2001:db8:64::cb00:7105` with the provider's prefix) and returns it.
3. The client connects to that IPv6 address like any other.
4. Routing carries the packets to the NAT64 box, which translates them. The client never learns that IPv4 was involved.

<Nat64Schema />

| Packet | Source | Destination |
|---|---|---|
| IPv6, client6 to NAT64 | `2001:db8:1234:1::d` (client6) | `64:ff9b::cb00:7105` |
| IPv4, NAT64 to server4 | a pool address, recorded in the NAT table (stateful) | `203.0.113.5`, the prefix dropped (stateless) |

Here DNS does more than answer a question: it steers traffic toward the translator. Content delivery networks and load balancers steer clients the same way, by choosing which address to return.

## Configuring an Interface

Every exchange so far assumed that hosts are configured.

A host's IP interface needs four items.

1. its IP address,
2. its subnet mask,
3. the IP address of its default gateway,
4. the IP address of a DNS server.

The four items are set manually or automatically: in IPv4 by DHCP, in IPv6 by stateful DHCP or by SLAAC (stateless) plus stateless DHCP. A router's interface toward a provider needs configuring too. In IPv4 it uses **PPP** (Point-to-Point Protocol), which configures telecom lines such as modems and ADSL automatically. In IPv6 it uses PPP, or DHCP with prefix delegation.

**DHCP (Dynamic Host Configuration Protocol).** A protocol by which a server hands hosts their configuration. In IPv4 that is all four items, the DNS server included. In its **stateful** form, the server also remembers which address it gave to which host.

The DHCP exchange is a two-phase commit, with four messages in IPv4.

1. The host discovers a DHCP server: **DISCOVER**.
2. The server returns an offer: **OFFER**.
3. The host commits to the offer: **REQUEST**.
4. The server confirms the commitment: **ACK**.

After the commitment, the server keeps state, the **lease**: the binding of the address to the client. A lease is valid for a limited time, and the client renews it to keep the address.

The host does not know the server's IP address, so it reaches the server by IPv4 broadcast or IPv6 multicast. An IPv4 DISCOVER carries the client's MAC address and travels in UDP from port 68 to port 67. Its source is `0.0.0.0` (the host has no address yet) and its destination `255.255.255.255` (everyone on this LAN). A broadcast never leaves the LAN, so either the server sits in the same LAN or the gateway relays the messages.

**DHCP relay.** A gateway that picks up its LAN's DHCP messages and forwards them to a DHCP server in another network, so that one server can serve many subnets.

<DhcpRelaySchema />

Without DHCP, IPv4 has a last resort.

**IPv4 self-autoconfiguration.** When no DHCP server is available and nothing is configured manually, an IPv4 host configures a link-local address by itself when it boots.

The host takes two steps.

1. It picks an address *at random* from the link-local block `169.254.0.0/16`.
2. It runs an **address duplication test**, checking that no other host on the link already uses that address. The host broadcasts an **ARP probe** for the chosen address: an ARP request, the IPv4 message asking "who has this IP address?", sent with sender IP `0.0.0.0` because the host has no address yet. The host keeps the address if nobody answers.

Self-autoconfiguration lets hosts talk on unmanaged or router-less local networks, as old AppleTalk networks did. It is not meant for general use. Windows implements it; Linux does not always.

## Autoconfiguration in IPv6

IPv6 can configure a host without a DHCP server.

**SLAAC (Stateless Address AutoConfiguration).** An IPv6 host builds its own addresses, first a link-local one and then a global one from a prefix announced by a router, with no server keeping state.

1. **Link-local address.** The host takes the prefix `fe80::/64`, at the start of the link-local block `fe80::/10`, and appends a 64-bit host part, derived in one of five ways:
   - manually, e.g. `::1`;
   - from the MAC address, by **modified EUI-64**;
   - randomly, with **temporary** validity;
   - by "secure autoconf" (RFC 7217), random but specific to each subnet;
   - cryptographically, from a hash of the host's public key.
2. **Address duplication test.** The host checks that no neighbour already uses the address by sending a query for it to the address's **solicited-node multicast address**: the prefix `ff02::1:ff00:0/104` followed by the last 24 bits of the host part.
3. **Global address.** The host sends a **router solicitation (RS)** to the all-routers multicast address `ff02::2`. A router answers with a **router advertisement (RA)** carrying a /64 prefix, and the host appends its host part to that prefix. SLAAC ignores a prefix that is not 64 bits long.

**Modified EUI-64.** The 64-bit host part derived from a 48-bit MAC address. Split the MAC address into its two 3-byte halves, insert `ff:fe` between them, and flip the second-lowest bit of the first byte.

**Example 5. A MAC-derived address.**

*The EPFL host lrcmac4 has MAC address `08:00:20:78:30:f9`. Inserting `ff:fe` gives `08:00:20:ff:fe:78:30:f9`, and flipping the bit turns `08` = 0000 1000 into 0000 1010 = `0a`. The host part is `0a00:20ff:fe78:30f9`, so the MAC address stays visible in lrcmac4's global address. Its link-local address is `fe80::a00:20ff:fe78:30f9`, and its duplication test goes to `ff02::1:ff78:30f9`. From an RA announcing `2001:620:618:1ad::/64`, lrcmac4 forms the global address `2001:620:618:1ad:a00:20ff:fe78:30f9`.*

SLAAC is fully automatic but gives no DNS server address, which a host gets in one of two ways.

- **Stateless DHCP.** A DHCP server that keeps no lease state and gives the DNS server's address to every host that asks.
- **RA option** (RFC 8106). As for the prefix, the host asks the link's routers by multicast, and a router adds the DNS server's address to its RA. Routers may also send RAs periodically, unasked, to all nodes at `ff02::1`.

An RA carries the prefix and, optionally, the DNS server's address, and the router that sends it becomes the host's default gateway. One RA thus covers all four items.

**Example 6. What does SLAAC give an IPv6 host?**

*A link-local address, and a global unicast address if a router is present in the subnet. Never a global address without a link-local one: the link-local address comes first, and a global one is added only when an RA arrives.*

A MAC-derived host part is the same on every network the host joins, so anyone who collects addresses can track the host as it moves. Two kinds of host part prevent this tracking.

**Temporary address.** An address with a random host part and a limited lifetime.

A temporary address passes through four states:

1. **tentative**, until the duplication test succeeds;
2. **preferred**, in normal use, until the preferred timer expires;
3. **deprecated**, no longer used to start new TCP connections, until the validity timer expires;
4. **invalid**.

**RFC 7217 address ("secure autoconf").** An address whose host part is not fully random but intractable:

$$
\text{host part} = \text{hash}(\text{interface id},\ \text{subnet prefix},\ \text{secret key})
$$

The secret key is obtained when the operating system is installed. The address stays the same whenever the host returns to the same subnet and changes unpredictably from one subnet to another, whereas a temporary address changes over time on the same network. Temporary and RFC 7217 addresses are the temporary and stable addresses that sit side by side on one interface, among which source address selection picks.

An IPv6 home receives a whole block of addresses, not one address. Its devices configure themselves by SLAAC, so its router needs a prefix to advertise. The Internet service provider (ISP) configures that router with DHCP, extended to hand over the block.

**DHCP with prefix delegation.** DHCP in which the ISP's DHCP server, the **delegating router**, gives the home router a whole prefix instead of one IPv6 address. The home router advertises that prefix to its devices. If the prefix of the link between the ISP and the home router lies inside the delegated prefix, the link prefix is excluded from the delegation (RFC 6603).

**Example 7. A delegated /60.**

*Swisscom delegates `2004:aaaa:bbbb:cc00::/60` to the home's edge router R0. The /60 holds $2^{64-60} = 16$ /64 prefixes, `cc00` to `cc0f` in the fourth hextet. R0's WAN address is `2004:aaaa:bbbb:cc01` followed by R0's EUI-64 host part, so the ISP link uses `2004:aaaa:bbbb:cc01::/64`, which is excluded. R0 advertises `2004:aaaa:bbbb:cc02::/64` on the home LAN, where hosts B and C append their own host parts. The remaining 14 prefixes are free for further home subnets.*

## Hop Limit and Traceroute

Forwarding tables change when a link fails or routes are recomputed. Because of propagation latency, the change reaches different routers at different times. In between, two routers may each forward a destination's packets to the other: a **transient loop**. A packet caught in the loop bounces back and forth. When the propagation time is small compared to the transmission time, a single packet, or a few, can keep the line busy and congest it.

**Hop Limit (IPv6) / Time to Live (IPv4).** An 8-bit field (0 to 255) in every IP packet, decremented at every IP hop. It exists to kill packets caught in transient loops.

- **Who decrements.** Every router and every NAT decrements HL/TTL. Switches do *not*.
- **Initial value.** 64 at the source, in principle.
- **Expiry.** When HL/TTL reaches 0, the packet is discarded.

*Hop limit counts routers, not links: a device that only switches frames inside a LAN never looks at it.*

**Example 8. A packet with hop limit 1.**

*A host generates a packet with Hop Limit = 1. Is the packet invalid? No. A router can never forward it, because decrementing the hop limit would give 0. A switch can, because a switch does not examine the IP header. Sources set HL = 1 to guarantee that the packet stays in the LAN.*

The same counter can map a path.

**Traceroute.** A tool that discovers the routers on the path to a destination by making each of them, in turn, report an expired packet.

1. The source sends a series of UDP probes to the destination, with TTL = 1, then 2, then 3, and so on.
2. The router where a probe's TTL expires discards it and sends an **ICMP error message** (time exceeded) back to the source.
3. The source learns that router's IP address from the source address of the error message, so the probe with TTL $n$ reveals the $n$-th router.

The last probe reaches the destination, whose answer tells the tool it has arrived. For UDP probes, that answer is an ICMP error saying that no application listens on the probed port. Linux and macOS send UDP probes by default, `traceroute -I` sends ICMP echo requests instead, and Windows' `tracert` uses ICMP. The names in the output come from a reverse DNS query (address to name) made by the tool, not from the routers. A `*` means that no reply arrived for that probe.

Beyond hop limit and the addresses, the IP header carries these fields.

| Field (IPv4 / IPv6) | Content |
|---|---|
| Type of Service / Traffic Class | 6 bits of **Differentiated Services**, roughly a priority (e.g. for voice over IP), honoured only within networks under a single administration; 2 bits of **Explicit Congestion Notification** |
| Total Length / Payload Length | size in bytes, *including* the header in IPv4, *excluding* it in IPv6; at most 65 535 bytes, and in practice limited by the link's MTU |
| Header Checksum (IPv4 only) | protects the header against bit errors; absent in IPv6, where data link and network layer hardware is assumed to detect errors efficiently |

**MTU (Maximum Transmission Unit).** The largest packet a data link layer carries in one frame: 1500 bytes for Ethernet.

Besides 6 (TCP), 17 (UDP), 1 (ICMP) and 58 (ICMPv6), the Protocol / Next Header field can name tunnels and security protocols.

| Protocol / Next Header | Upper layer |
|---|---|
| 4 | IPv4, encapsulated in IP (a tunnel) |
| 41 | IPv6, encapsulated in IP (a tunnel) |
| 50 | ESP, an encrypted payload |
| 51 | AH, an authentication header |

## From IP Address to MAC Address

Within a subnet, the MAC layer moves the data, so every frame needs the MAC address of the neighbour it is sent to.

**MAC address resolution.** Finding the MAC address that belongs to an IP address in the same subnet. Host A has a packet for a neighbour B in its subnet and knows only B's IP address. B is either the final destination, delivered directly, or the next hop toward it, such as the default gateway. A broadcasts (IPv4) or multicasts (IPv6) the question "who has the IP address of B?" to the LAN. All hosts listening to that IP address, in principle only B, answer with their MAC address.

*Resolve the neighbour the frame goes to, never the far destination: MAC addresses are local, so only a neighbour's is needed.*

**NDP (Neighbor Discovery Protocol).** IPv6's address-resolution protocol. Its messages are ICMPv6 packets, carried inside IPv6 packets with next header 58 (`0x3a`).

- **Neighbor Solicitation (NS).** The question "who has IP address B?".
- **Neighbor Advertisement (NA).** The answer, giving B's MAC address.

SLAAC's router solicitations and advertisements are NDP messages too, and its duplication test is an NS for the host's own tentative address.

**Neighbor cache.** A host's table of the IP address to MAC address mappings learned by address resolution. Entries expire after a configurable time of inactivity. Positive feedback from higher-layer protocols may extend an entry's validity.

On one LAN, A has address `2001:620:618:1a6:1:80b2:f01:1` and MAC `08:00:20:71:0d:d4`, B has `2001:620:618:1a6:1:80b2:f66:1` and MAC `00:00:d0:b3:d2:8d`, and C and D are other hosts.

1. A sends an NS, "who has `2001:620:618:1a6:1:80b2:f66:1`?". Its destination IP is B's solicited-node multicast address `ff02::1:ff66:1`, whose last 24 bits are copied from B's address. Its destination MAC `33:33:ff:66:00:01` is derived from that multicast address in a similar way.
2. B answers with an NA giving its MAC address, sent straight back to A: destination IP `2001:620:618:1a6:1:80b2:f01:1`, destination MAC `08:00:20:71:0d:d4`.
3. A stores B's MAC address in its neighbor cache and sends the data to B, e.g. a TCP packet to IP `2001:620:618:1a6:1:80b2:f66:1` and MAC `00:00:d0:b3:d2:8d`.

The solicited-node multicast address keeps the NS from bothering the whole LAN. It is a link-scope multicast group, and every host listens to ("subscribes to") the group of each of its addresses. A packet sent to the group reaches all hosts whose address has the same last 24 bits, normally only the target. The frame's destination MAC address is `33:33` followed by the last 32 bits of the destination IP address, and every other host discards the frame on that MAC address alone. Solicited-node addresses exist only in IPv6, where NDP and other protocols use them. IPv4 uses broadcast instead.

**ARP (Address Resolution Protocol).** IPv4's address-resolution protocol. ARP does NDP's job.

ARP differs from NDP in three ways.

- **Terminology.** The NS and NA are called **ARP request** and **ARP reply**, and the neighbor cache is called the **ARP table**.
- **Protocol type.** ARP packets are not ICMP packets and are not even carried in IP packets. They sit directly in the MAC frame, with Ethertype `0x0806`.
- **Reachability.** The ARP request is broadcast to all nodes of the LAN, not multicast.

A captured ARP request:

```text
Ethernet II
    Destination: ff:ff:ff:ff:ff:ff (ff:ff:ff:ff:ff:ff)
    Source: 00:03:93:a3:83:3a (Apple_a3:83:3a)
    Type: ARP (0x0806)
    Trailer: 000000000000000000000000000000000...
Address Resolution Protocol (request)
    Hardware type: Ethernet (0x0001)
    Protocol type: IP (0x0800)
    Hardware size: 6
    Protocol size: 4
    Opcode: request (0x0001)
    Sender MAC address: 00:03:93:a3:83:3a (Apple_a3:83:3a)
    Sender IP address: 129.88.38.135 (129.88.38.135)
    Target MAC address: 00:00:00:00:00:00 (00:00:00_00:00:00)

```

The frame goes to the broadcast MAC address `ff:ff:ff:ff:ff:ff`, and its type names ARP, not IP, as the higher-layer protocol. Inside, the protocol type `IP (0x0800)` names the protocol that asked for the resolution (IP meaning IPv4). The target MAC address is all zeros because that address is what the request asks for. The ARP probe of IPv4 self-autoconfiguration is such a request with sender IP `0.0.0.0`. On a Linux host, `ip route show` gives the gateway's IP address and `arp -a` lists the ARP table, where the gateway's MAC address appears once resolved.

Because resolution asks only the sender's own link, a link-local address on another link cannot be reached: its NS goes out where nobody holds the address.

## Securing Address Resolution

ARP and NDP believe whoever answers, and nothing authenticates the answer.

**ARP spoofing.** An attack in which a forged ARP reply or NA makes a victim map another host's IP address to the attacker's MAC address.

1. The attacker sees A's request for B's MAC address (easier in IPv4, where ARP requests are broadcast to everyone).
2. The attacker sends a bogus ARP reply or NA carrying its own MAC address.
3. If the bogus answer reaches A before B's, A may map B's IP address to the attacker's MAC address and send B's traffic to the attacker.

**Rogue RA.** A router advertisement from a host that is not a legitimate router. A single rogue RA makes its sender everyone's default gateway on the link. Rogue RAs are not always attacks: most are accidental, from misconfigured virtual machine hosts or Windows internet connection sharing.

ARP spoofing and rogue RAs both open the way to a **man-in-the-middle attack**: the attacker receives the victims' traffic, can read or alter it, and can pass it on so that nobody notices.

Mitigations sit in the LAN switch or the WiFi base station, which sees every frame.

- **DHCP snooping.** The switch or WiFi base station observes all DHCP traffic and remembers the IP address ↔ MAC address mappings the DHCP server hands out. Two defences build on these mappings:
  - **Dynamic ARP inspection.** The switch filters all ARP (or NDP) traffic and allows only valid answers, removing invalid broadcasts (IPv4) and multicasts (IPv6).
  - **ARP proxy.** The WiFi base station answers ARP requests itself.
- **RA guard** (RFC 6105). The switch drops RAs arriving on ports where no router exists.

These defences are deployed in enterprise networks, rarely at home or on WiFi base stations.

The cryptographic alternative makes the answer itself verifiable.

**Public-key cryptography.** Each party holds two keys: a public key $P$, shared with everyone, and a private key $p$, kept secret. What one key encrypts, only the other decrypts.

**Digital signature.** The signature of a message $m$ is $p(m)$, the message encrypted with the sender's private key. The sender sends $m$ and $p(m)$. The receiver decrypts the signature with $P$ and checks it against $m$. If the check fails, $m$ is discarded as forged. If it succeeds, only the owner of $p$ can have signed $m$.

**SEND (Secure Neighbor Discovery).** NDP in which each address is bound to its owner's public key and each NA is signed, which makes NDP spoofing impossible. SEND uses **cryptographically generated addresses (CGAs)**, the fifth kind of SLAAC host part.

1. B creates an RSA key pair, private key $p$ and public key $P$.
2. B computes a CGA whose host part is a hash of $P$, the IPv6 prefix and other CGA parameters such as counters. The hash binds B's IP address to $P$.
3. B includes $P$ and all CGA parameters in its NA and signs the NA with $p$. The signature binds the NA to the key pair, and through it to the CGA.
4. A checks that the CGA matches $P$ by recomputing the hash from $P$ and the NA's parameters, and that the sender owns the key pair by checking the signature with $P$.

$$
\text{host part} \approx \text{hash}(P,\ \text{IPv6 prefix},\ \text{CGA parameters})
$$

NAs may also carry **nonces**, values used only once, so that an attacker cannot replay an old valid NA. Anyone can compute a CGA bound to a public key $P$. What an attacker cannot produce is a valid signature, which only the owner of $p$ can issue.

SEND solves the problem but requires a strong hash function (SHA-1 is currently used) and may need a trusted certification authority (e.g. RPKI), so it is not widespread yet.
